# 実行枠制御の形式検証

## 性質と害

- 同じキャッシュルートの `locks/` を共有し、全員が同じ上限を使う主体群では、同時保持数が既定の2件または設定値の1件を超えない。
  上限1では枠0だけを使う。
  破ると共有資源が枯渇するか、枠0を共有する旧版と排他できない。
- 新版が登録順を越えて取得できるのは、先行要求がすべて旧版で、枠1以降を取る場合だけである。
  破ると先行要求の順序が逆転するか、旧版が使えない空き枠まで遊ぶ。
- 保持者が有限時間で解放し、取り消されない待機者が再試行できるなら、全員が取得できる。
  破ると検証が終わらない。

## 対象と探索範囲

`pyfltr/command/execution_slot.py` の `slot_count`、`_slot_paths`、`_acquire`、`_release` を直接呼ぶ。
各調停区間の取得枠または待機を仕様から求めた結果と比較し、解放では保持中の枠だけが空くことを確認する。
待機列の登録順、枠の占有、要求の進行段階を状態として保存する。

1つのロック先で4主体が各1回要求する。
上限2・1それぞれで旧版と新版の全16通りの配置を探索する。
1手順は末尾登録（`_request` の調停ロック区間）、取得可能な最初の空き枠の取得（`_acquire` の調停ロック区間）、成功した要求の除去（`_request` の終了時の調停ロック区間）、または枠の解放（`_release`）。
旧版は先頭で枠0だけを取る主体として表す。
通常解放と異常終了による占有解除は同じ遷移とする。

同じ状態からの遷移は履歴に依存しないため、同じ状態は再展開しない。
候補のない再試行は状態を変えないため省く。
状態を変える手順は各主体につき最大4回で逆戻りしない。
全員終了以外の終端がないことと、解放・再試行の機会が与えられる前提を合わせて、この範囲でデッドロックと飢餓がないことを検査する。

## 前提と保証外

枠ロック、登録済み待機列、調停ロック、保持者記録の入出力はモデルで置き換える。
再試行は実装の待機時間に入った地点で区切る。
枠ロックは排他的であり、登録と調停は直列化されると仮定する。
異常終了した待機ファイルは次の調停前に回収されると仮定し、回収処理自体は検査しない。
同時保持の別上限設定、再入・祖先からの継承、取消、繰り返し登録、OSの `flock` / `msvcrt.locking` 自体、ファイルシステム破損、電源断は対象外。
異なるキャッシュルートは別のロック先であり、本検査は1つの先だけを扱う。

## 再実行

リポジトリルートで実行する。
Pythonと既存の開発環境だけで調停関数の変更を検出でき、外部のモデル検査器を要しない。
通常のテスト収集とは別に、実行枠の変更時に明示して起動する。

```bash
uv run --frozen python .claude/skills/verify-execution-slot/check.py
```

終了コード0と両上限の状態数を確認する。
失敗時は上限・旧版の配置・違反に至る操作列、または設定やロック名の不一致が出る。
